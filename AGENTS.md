# AGENTS.md

- Build: `npm run build` (tsc → `dist/`). ESM, NodeNext; import with `.js` suffixes.
- Style: functional. Pure builders/validators return `Result<AppError, A>`; no thrown exceptions. Side effects (reading and writing the `.ics` files) only in the thin effect layers (`src/reader.ts`, `src/vdir.ts`); everything else is pure. There is no khal and no subprocess: the server parses and writes iCalendar files itself.
- User-supplied values (calendar names, uids, dates, times, durations, zone names, text) are validated before use: dates and times by the strict parsers in `src/range.ts`, zones by `ianaZone` (`src/timezone.ts`), text by the ICS escaping in `src/ics.ts`, calendar and uid by length and the vdir lookup (a calendar is addressed by its configured `path`, never by a path from a call; file names are plain tokens).
- Update README.md when tools change.
- No function reads `process.env`, the home/tmp directory, the clock, the host time zone, random values or the config file itself. `src/index.ts` and `src/cli.ts` (the process edge) read them once and pass them on: environment, config and host zone become a `Settings` object (`src/settings.ts`), the uid and clock are injected (`ServerDeps`). Keep functions pure where possible; tests build `Settings` with `testSettings` (`src/testlib.ts`) instead of mutating global state.
- Time zones: the host zone is `Settings.timezone` (an IANA name, read once at the edge from `Intl.DateTimeFormat().resolvedOptions().timeZone`, which honours `TZ`); there is no config key for it, and nothing else asks the host. Recurrences are expanded as wall-clock time in the event's own zone (`src/expand.ts`), so a daily 09:00 stays 09:00 across DST changes; days are added as calendar days, never as 24 hours. Input without a zone means the host zone, `timezone` names another IANA zone, and a TZID the server cannot resolve is an error or a reported problem, never a silent guess. Every timed event written gets a `VTIMEZONE` generated from the IANA zone (`src/vtimezone.ts`, RRULE based), and an incoming `VTIMEZONE` is preserved. Tests that depend on zones pass the zone explicitly; they never rely on the machine's `TZ`.
- Validation: everything read from the environment or the config is trimmed and checked at startup, and independent problems accumulate (`src/validation.ts`: `Validated<A>`, a `Result` with a non-empty list of problems; effect 4 has no `Validation` module) so all of them are reported at once. Pure value checks live in `src/config.ts` / `src/settings.ts` (`loadSettings`), checks against the machine (the calendar directories can be read and written, the temp dir) in `src/preflight.ts`, run only by `src/index.ts`. `Result.flatMap` is for dependent steps only. A new config key needs a check in both places that apply and a test for each rejected value.
- Agents MUST ASK the user before any destructive or write operation (e.g. deleting or overwriting files, rewriting git history, changing calendars). Every MCP tool that writes (`new_event`, `update_event`, `end_event_series`, `respond_to_event`) must say so in its description ("WRITE OPERATION … ask the user for confirmation"); read-only tools must keep working on read-only calendars. A tool that changes or removes existing data (it overwrites a calendar file, nothing is kept) must also say that it cannot be undone. Ask the user whenever a change is irreversible, in this repository's own work as well (no pushes, tags or history rewrites without asking).
- Files: reading skips files over 2 MiB and reports unreadable or duplicate-uid files as problems next to the result (never silently dropped); writes go to a temporary file in the same directory and are renamed over the old one, new files never overwrite an existing one (`O_EXCL`-style create). vdirsyncer may run at any time, so re-check the file right before writing.
- Nix: `flake.nix` + `nix/` (package, Home Manager module). Verify with `nix flake check --no-build`; format with `nix fmt <files>`. Update `npmDepsHash` in `nix/package.nix` when `package-lock.json` changes, which includes every version bump (the lockfile carries the root version). The version also lives in `src/server.ts`. The dev shell has Node and the hooks only; nothing needs Python.
- Tests: `npm test` = `tsc -p tsconfig.typecheck.json` + `vitest run --coverage` (`src/*.test.ts`, helpers in `src/testlib.ts`). Code that touches files is tested on `mkdtemp` directories only, which are removed afterwards. Coverage thresholds in `vitest.config.ts` (lines/statements/functions 90, branches 85) fail the run; `src/cli.ts` and `src/index.ts` are covered only end to end via the spawned server in `src/mcp.test.ts` (rebuilt by `vitest.global-setup.ts`) and are excluded from the thresholds. Add tests for every function you change. There are no integration tests against an external calendar tool; round trips (create, read back, edit) run in the unit suite on temporary directories.
- Conformance: every requirement of the specs lives in a registry (`spec/rfc5545.json`, `spec/scheduling-storage.json`; ids like `RFC5545:3.3.10:count-xor-until`, `RFC5546:…`, `RFC6868:…`, `RFC4791:…`, `RFC7986:…`, `VDIR:…`, `POLICY:…`) with level, quote, scope and status (`required`, or `n/a`/`deferred` with a reason). A test proves a requirement by being written `itReq(id | [ids], name, fn)` (`src/testlib.ts`), which puts the id in the test name; suites are in `src/conformance/*.test.ts`. `src/conformance.meta.test.ts` fails on duplicate ids, on a citation of an unknown id and on a required row without a test; `spec/uncovered.json` is a ratchet that may only shrink, and `docs/conformance.md` is the generated report. After adding or covering requirements run `UPDATE_CONFORMANCE=1 npx vitest run src/conformance.meta.test.ts` and commit both files. Never cite an id with a test that does not prove it; a rule the server does not interpret gets `n/a` with the reason. Vendor quirks (Outlook, Zimbra, Google, Apple, Thunderbird) are tolerated on read only, tested in `src/conformance/vendors.test.ts`, and never reproduced in what we write.
- CI: always use the Nix shell: every build/test/lint/pack step runs as `nix develop --command …`, never with tools from the runner image (Node, npm, convco); Nix store and `~/.npm` are cached. `.github/workflows/ci.yml` (nix flake check + build on Linux/macOS, npm build/test, convco on PRs; the release needs `nix` and `npm`). A tag `vX.Y.Z` creates a GitHub release and must equal the `package.json` version; never create or push tags without asking the user.
- Per-calendar settings are one typed object per calendar (`CalendarConfig` in `src/config.ts`, `calendars.<name> = { path, email?, alarm? }`), never parallel maps; add a field to that interface, to `parseCalendar`, to the Home Manager submodule and to the example together. `path` (the calendar's vdir, an absolute path, unique per calendar) is required: a calendar without it does not exist. Reminders exist only per calendar (no global default); `defaultCalendar` is required when several calendars are configured (checked in `src/preflight.ts`), never guessed, and `new_event` always names its calendar. Never depend on the order calendars are listed in (sort anything shown). There is no khal: nothing in the code, the config or the environment refers to a khal program. Every config key has an environment variable of the same name by one schema (`MCP_KHAL_` + the key path in capitals joined by single `_`: `defaultCalendar` -> `MCP_KHAL_DEFAULT_CALENDAR`, `calendars.<name>.path|email|alarm` -> `MCP_KHAL_CALENDARS_<NAME>_PATH|EMAIL|ALARM`, `<NAME>` = the calendar name in capitals with runs of other characters as one `_`); `parseConfigWithEnv` (`src/config.ts`) lays the environment over the file, a value is checked once and a problem names the variable that supplied it. A new config key needs its variable (and tests) in the same change, plus a line in the README table.
- Config keys (`src/config.ts`) and `examples/mcp-khal.json` move together: `src/examples.test.ts` parses the example, the Home Manager module (`nix/hm-module.nix`, checked by `nix/module-check.nix`) mirrors every key and the README documents them. The Nix package installs the example under `share/doc/mcp-khal/examples/`.
- Hooks (via `nix develop`): nixfmt, biome (`biome check --write`), ripsecrets, unit tests, convco. Commit messages must be Conventional Commits; commits fail if tests fail.
