# AGENTS.md

- Build: `npm run build` (tsc → `dist/`). ESM, NodeNext; import with `.js` suffixes.
- Style: functional. Pure builders/validators return `Result<KhalError, A>`; no thrown exceptions. Side effects only in `runKhal`.
- User-supplied values must pass `safeToken` (no leading `-`, no control chars); positionals follow `--`.
- Update README.md when tools change.
- No function reads `process.env`, the home/tmp directory, the clock, random values or the config file itself. `src/index.ts` and `src/cli.ts` (the process edge) read them once and pass them on: environment and config become a `Settings` object (`src/settings.ts`), the uid and clock are injected (`ServerDeps`). Keep functions pure where possible; tests build `Settings` with `testSettings` / `FakeKhal.settings()` instead of mutating global state.
- Validation: everything read from the environment or the config is trimmed and checked at startup, and independent problems accumulate (`src/validation.ts`: `Validated<A>`, a `Result` with a non-empty list of problems; effect 4 has no `Validation` module) so all of them are reported at once. Pure value checks live in `src/config.ts` / `src/settings.ts` (`loadSettings`), checks against the machine in `src/preflight.ts`, run only by `src/index.ts`. `Result.flatMap` is for dependent steps only. A new config key needs a check in both places that apply and a test for each rejected value.
- Agents MUST ASK the user before any destructive or write operation (e.g. deleting or overwriting files, rewriting git history, changing calendars). Every MCP tool that writes (`new_event`) must say so in its description ("WRITE OPERATION … ask the user for confirmation"); read-only tools must keep working on read-only calendars.
- Nix: `flake.nix` + `nix/` (package, Home Manager module). Verify with `nix flake check --no-build`; format with `nix fmt <files>`. Update `npmDepsHash` in `nix/package.nix` when `package-lock.json` changes, which includes every version bump (the lockfile carries the root version). The version also lives in `src/server.ts`.
- Tests: `npm test` = `tsc -p tsconfig.typecheck.json` + `vitest run --coverage` (`src/*.test.ts`, helpers in `src/testlib.ts`, fake `khal` on PATH for effectful code). Coverage thresholds in `vitest.config.ts` (lines/statements 99, functions 98, branches 95) fail the run; `src/cli.ts` and `src/index.ts` are covered only end to end via the spawned server in `src/mcp.test.ts` (rebuilt by `vitest.global-setup.ts`) and are excluded from the thresholds. Add tests for every function you change.
- Integration tests: `nix develop --command npm run test:integration` runs `src/*.integration.test.ts` against the real khal (not part of `npm test`). They must only use temporary directories: HOME, XDG_*, TMPDIR, khal's config and calendars and the mcp-khal config all live in one `mkdtemp` sandbox that is removed afterwards; the environment given to khal is built from scratch (only PATH is taken over).
- CI: always use the Nix shell: every build/test/lint/pack step runs as `nix develop --command …`, never with tools from the runner image (Node, npm, convco); Nix store and `~/.npm` are cached. `.github/workflows/ci.yml` (nix flake check + build on Linux/macOS, the integration tests as a job of their own on Linux/macOS, npm build/test, convco on PRs; the release needs all of them). A tag `vX.Y.Z` creates a GitHub release and must equal the `package.json` version; never create or push tags without asking the user.
- Per-calendar settings are one typed object per calendar (`CalendarConfig` in `src/config.ts`, `calendars.<name> = { email?, alarm? }`), never parallel maps; add a field to that interface, to `parseCalendar`, to the Home Manager submodule and to the example together. Reminders exist only per calendar (no global default); `defaultCalendar` is required when khal has several calendars (checked in `checkCalendars`, `src/preflight.ts`), never guessed, and `new_event` always passes `-a`: khal's own `default_calendar` is never relied on. Never depend on the order khal lists calendars (sort anything shown). `MCP_KHAL_BIN` and the config's `khal` follow one rule (`checkBinary`): a bare command name or an absolute path, never a relative path.
- Config keys (`src/config.ts`) and `examples/mcp-khal.json` move together: `src/examples.test.ts` parses the example, the Home Manager module (`nix/hm-module.nix`) mirrors every key and the README documents them. The Nix package installs the example under `share/doc/mcp-khal/examples/`.
- Hooks (via `nix develop`): nixfmt, biome (`biome check --write`), ripsecrets, unit tests, convco. Commit messages must be Conventional Commits; commits fail if tests fail.
